Overview

Form Skate Workbench is an IDE for one program, a skateboard game built on @form/core: code, notes, docs, a textbook, a coding agent and a drafting-sheet stage share one window of tiled views, and every view is there to read or change the running program. This system is the workbench's look and its writing: the Kiln style of the shell, panels and reading views (Swiss: white ground, one ink, Arial in two weights, 1 px rules, red only for trouble and selection), and how to write its interface copy, notes, docs and book chapters.

Two neighbouring systems cover the rest. Form Skate Agent (https://claude.ai/artifact/4KJ4g867ubqBbVszAeqXWM) is the agent panel: how the agent works, its chat, steps and threads. Form Skate Stage (https://claude.ai/artifact/J3P5XmY4B7uyZJZzgLaZYy) is the stage: the 2.5D drafting look, the camera, line weights and the overlays drawn on the canvas (chips, trick toast, fail banner). A new panel uses this system; anything drawn on the stage uses the Stage system.

Using this system

  • Tokens: colours by their Kiln names (--bg, --ink, --ink-2, --hair, --rule, --fill, --code-bg, --accent, --sel, --tok-*), font sizes --fs-xs to --fs-xl, families --font-ui, --font-display, --font-code. In the app's own stylesheet the families are --mono (which is Arial), --display and --code.
  • Components are CSS classes on plain markup, in components/bundle.css (the rules copied from app/kiln.css and app/skate.css). There is no script bundle: the app renders the same markup from React (app/ui/*.jsx), and any markup with these classes looks the same. Each component's README gives the markup to write.
  • Fonts: nothing to load. The interface is Arial ("Helvetica Neue", Helvetica, sans-serif); code is the system monospace (ui-monospace, Menlo, Consolas). IBM Plex Mono belongs to the stage only.
  • Themes: light is the default and dark mirrors it; the viewer's choice cycles system → light → dark from the header and sets data-theme on the root. Style through tokens only; no rule names a colour.
  • Where it lives in the code: app/kiln.css and app/skate.css (styles), app/ui/app.jsx (header, layouts), dock.jsx (tiles), common.jsx (Seg, Tog, Menu), code.jsx, panels.jsx, notes.jsx, book.jsx, app/markdown.js (reading views), app/highlight.js (code colours), app/bookexport.js (HTML, EPUB, Markdown export).

Content fundamentals

The workbench talks like a lab notebook: plain, exact, measured. The full guide is the section Writing interface copy; the rules most often needed:

  • Name things by what they are in the program: "systems", "signals", "states", "params", "pin trace", "hot edit", "fresh world". Use the program's ids as written (pop/snap, skater/stance) in the code face.
  • Sentence case for buttons and menu titles ("Export project", "Square up"); lowercase for small descriptions, placeholders and abouts ("the drafting sheet you skate on", "search the shelf"). View names are one capitalised word: Notes, Docs, Book, Code, Agent, Reference, Stage, Graph, IR, Traces, Events, Params, Experiments.
  • Numbers with units, a space between: "4.29 m/s", "0.08 m", "15 rad/s", "160 N", "1/120 s". Times in seconds with two decimals on the clock and three in logs. Join related facts with " · " ("16 systems · 15 signals · 42 states"), multiply with × ("combo ×2", "1×").
  • Say what happens and what to do next: "No traces pinned. Type above to add one, or click pin trace in the inspector." Errors name the thing that failed, the place and the fix: "pop/pop stopped at 2.53 s: … Fix it and press Run (the world resumes), or Reset."
  • British spelling (centre, behaviour, colour). No exclamation marks, no emoji, no "please", no jokes.
  • The book has stricter rules (no em dashes, a banned-word list, numbers only from measurement): see Writing a book section.

Visual foundations

  • Ground and ink. Every surface is bg; text and marks are ink; secondary text is ink-2. There are no tinted panels and no cards: a region is separated by a 1 px hair rule, rows by a rule line. fill appears only on hover, on inline code chips and in a plain callout. Code sits on code-bg.
  • Lines are the structure. 1 px everywhere (hair for borders and tile edges, rule between rows, ink for emphasis: a menu's border, the rule above a doc section, the params panel's top). 2 px only for marks of state (a selected row's inset bar, a callout's rule, focus). 3 px once: above a part title in the Book.
  • Two weights. 400 and 700, nothing else. Bold marks the active tab, a value, a title, a defined term.
  • One red. accent means trouble or selection: errors, bails, the stopped clock, the selected row's bar, the selected graph node, a Try it callout, the ▸ after a lab: link, the chapter label, the caret. Never decoration, never a category colour. sel is its wash. Success is not coloured.
  • Square. border-radius: 0 on every control, menu, tile, toast and callout. The only round things are the radio mark in menus and the signals group in the graph.
  • Dense and quiet. Base text 12px at line height 1.45, controls 30px high, toolbars 46px, the header 52px. Paddings are small fixed values (see Spacing: 4, 6, 8, 10, 12, 14, 16px). No shadows anywhere in the UI (one exception: the Book's contents drawer in a narrow tile).
  • Numbers line up. Use font-variant-numeric: tabular-nums wherever digits change or stack: clocks, pills, values, tables, readouts.
  • Data without hue. Charts and plots are ink on the ground with ink-2 axes in 9.5px and rule grid lines. Tell series apart by dash (solid, 4 3, 1 2) and mark shape (circle, square, diamond, cross, triangle), never by colour; accent marks only the selected series or a failure.
  • Focus. :focus-visible draws a 2px ink outline offset 1px; inputs show focus by turning their border ink.
  • Motion. Almost none: a busy indicator blinks (0.8 s, two steps), the drop hint slides 0.08 s between targets, the Book's contents drawer slides 0.18 s (off under prefers-reduced-motion). Nothing fades in.
  • Dark theme. The same design with bg #1a1a1a, ink #f2f2f2, ink-2 #9a9a9a and a lighter red #ff3b4a; washes are stronger (sel 16%). Comments and punctuation in code get darker, not lighter, so they still recede.

Layout

  • Header bar (HeaderBar) across the top; under it the dock: tiles of tabbed views split by 1 px gutters (DockTile). Seven layouts ship ("Code beside the stage", "Stage first", "The program: code, graph, IR", "Reading the notes", "Experiments and traces", "Reading the book", "Everything in one tile"); people drag tabs to make their own, kept per browser. See Layouts and the dock.
  • A view is .tabbody: a Toolbar at the top, the body (a .scroll list, a document, a canvas, a diagram), optionally a 288px side column of Blocks on the right (aside.side), optionally a 30px hint bar at the bottom.
  • Responsive by tile, not window. A tile body is a size container: under 640px of tile width a view stacks its side column under its body; the Book and Docs fold their left column away under 700 and 620px. Under 640px of window the dock becomes one tile and the header drops pills and labels.
  • Reading width. Documents keep a 76ch measure (74ch in the Book) at 18px 22px padding, however wide the tile.

Iconography

There is no icon set. The workbench uses text glyphs in the UI font: ▶ ❚❚ ⏭ ⏮ ↺ (run controls), ‹ › (previous, next), × (close, unpin), + (open a view), ▾ (opens a menu), ▸ (after a lab: link), • (unsaved file), ● (recording), ▦ (layouts), and the declaration glyphs of the code gutter: ■ system, λ signal, ○ state, ◇ param, ◎ watch, ▢ view, △ thing. The theme switch is the one drawing: a 16px inline SVG (sun, moon, half disc) stroked in currentColor at 1.4, because those glyphs are missing from many fonts. Check marks are 9px squares (.tog::before, .box), filled ink when on. No emoji, no icon fonts, no logo: the name set in bold type is the mark. Building a new panel

  1. Register the view with a one-word title and a lowercase about (app/ui/app.jsx views), and render <div class="tabbody col">.
  2. Open with <div class="toolbar">: a .filter if the view lists things, Segmented and Toggle controls for its modes, .btn.sm commands, and a .lbl sentence that says what the view shows.
  3. Put the content in <div class="scroll">: rows with rule lines between them (.rt tables, .ev-style grids in the code face for logs), or a .doc for prose.
  4. For details of a selection add <aside class="side"> with Blocks: an h2 noun, a .sub, a .note, a dl.kv, .actions links. Use .nid for program ids so they select in the graph.
  5. Use .empty.padded for the empty state, .fail for a failure inside the view, host.toast for a passing confirmation.
  6. Colours only from tokens; the red only for errors and the selection; numbers tabular with units.
  7. If it draws (a canvas plot), read --ink, --ink-2, --rule and --accent from getComputedStyle at draw time, as Traces does, so it follows the theme.

docs-and-notes.md

Writing docs and preset notes

Besides the book, the workbench carries two shorter kinds of writing: preset notes, the guide to one preset shown in the Notes tab, and shelf docs, one topic each in the Docs tab. Both are Markdown with frontmatter, rendered like the book (see The Markdown the reading views render).

Preset notes

A preset is content/presets/<id>.md plus an optional folder content/presets/<id>/ holding files that replace the base library's (main.js, lab/chrono.js) or patch it (main.js.patch: blocks of //@@ find, //@@ replace, //@@ end, each of which must match once).

---
id: B-01
title: Flatground
group: Basics
about: The whole game, as the library ships it: a lot, a funbox, a board, a rider, fifteen tricks.
tries: Explain how a kickflip happens, from the key press to the trick event | Add a new trick to the recognizer and test it
pins: recognizer/height, recognizer/flipTurns, recognizer/shoveTurns
docs: workbench-tour, rigid-bodies, quaternions
overlays: shadows, trail, annotations, grid
view: axo
---
key is
id group letter and number: B Basics, P Physics, T Tricks, M Mechanisms, G Game feel, R Recognition, E Experiments, D Drafting (U for a viewer's own)
title the preset's name in the menu and the notes toolbar
group Basics, Physics, Tricks, Mechanisms, Game feel, Recognition, Experiments, Drafting
about one sentence, shown under the title in the preset menu and in related lists
tries questions for the agent, separated by |, offered as buttons in an empty thread
pins traces pinned when the preset loads

overlays, view, track, zoom, speed, chains, order the stage's starting settings

The body follows one pattern. A # title, then a lede that says what is on the screen and what the preset is for, then a Try it as early as possible so the reader acts before reading on, then ## sections that each explain one mechanism with a short code excerpt or formula, a Try it where it can be seen, and an Exercise at the end. Notes are shorter than chapters (500 to 1,000 words) and assume the reader has the workbench open: link generously with lab: links.

Shelf docs

content/docs/<nn>-<slug>.md, ordered by order:

---
id: springs
title: Springs, damping and critical damping
group: Control
about: The damped oscillator, ζ and ωₙ, overshoot, and the exact half-life springs used for smooth animation.
order: 24
---

Groups on the shelf: Start here, Maths, Mechanics, Control, Contact, The board, Computation, Drawing, Method. A doc covers one topic: it opens by saying what it covers and where the library uses it ("Springs are everywhere in the library: contact forces, the rider's legs, the foot guides, the camera…"), develops it in five to eight ## sections with the library's own numbers, and often ends with its limits ("When a spring is the wrong tool"). Point to the book chapter that goes deeper with [Chapter 9](lab:book?ch=9).

Voice

The same as the book's (see Writing a book section): plain, exact, the program's own names, real numbers, British spelling, no analogies. Notes and docs were written before the book's checker and use em dashes; new writing should follow the book's rule (a colon, a comma, parentheses or a new sentence) so text can move between notes, docs and chapters. The book checker does not run on notes and docs, but test/links.js checks their lab: links.

layouts-and-dock.md

Layouts and the dock

The workbench is one window: the header bar, then a dock of tiles. A tile shows one view at a time behind a strip of tabs; tiles sit side by side or stacked in nested splits. Everything about the arrangement belongs to the person using it and is kept in their browser (localStorage, key formskate.v1.layout).

The layout tree

A layout is a small tree (app/ui/dock.jsx): a tile { t: 'tile', views: [...], active } or a split { t: 'split', dir: 'row' | 'col', kids: [...], sizes: [...] } whose sizes are fractions that sum to 1. Unknown or duplicate views, empty tiles and one-child splits are removed when a layout loads; splits in the same direction merge.

On a phone (under 640px) the dock is always one tile with Stage first.

Moving things

  • Click a tab to show it; drag it onto another tile's tabs to move it there, onto the edge of a tile (the outer 22%) to split that tile on that side, or into its middle to add it as a tab. The drag shows where it will land (see DragFeedback).
  • Drag a gutter to resize; each side keeps at least 6%.
  • × closes a view (it goes to the + menu and the empty-tile picker); + opens a closed view in this tile.
  • Links bring views forward. A lab: link or an action that needs a view (host.focus({ view })) activates it in its tile, or adds it next to related views (Code near Notes and Agent, Traces near Events and Params…) if it was closed.

Designing a view for the dock

  • A view must work from about 320px to the full window in either direction. Use the tile container query (@container tile (max-width: 640px)) rather than media queries: the tile is what changes size.
  • At narrow widths stack the side column under the body (the shared rules do this for .tabbody and .page) and fold left-hand columns away behind a button (the Book's Contents).
  • Never assume a view is visible: it may be behind another tab. Do expensive drawing only while mounted.
  • Keep a view's own state (open file, chapter, scroll position) in the view or in store (formskate.v1.*), so closing and reopening a tab brings it back.

states-and-feedback.md

States, errors and feedback

The workbench runs a live program, so it is often in a state worth showing: edited and not yet run, compiling, stopped by an exception, recording, waiting for a long job. Each state has one place and one look.

Where each kind of feedback goes

situation where look
the program compiled the build pill ("ok", counts), the editor footer ("compiled in 7.6 ms · hot: kept …") ink
the program does not compile the pill ("2 errors", accent), the Code tab's badge (accent count), the error line (accent number, sel wash), the diagnostics list, the footer ("does not compile: …") accent
a warning from the compiler the gutter number bold ink, a "!" row in the diagnostics, a plain toast ink (errors get the red toast)
the running program threw the clock (" stopped" in accent), the pill ("stopped"), a banner on the stage (Form Skate Stage) with the system, time, message and source accent
unsaved edits " •" after the file, "edited" after the preset title, Run turns primary ink fill
something finished a toast ("Copied", "Saved as U-01") ink
something failed a red toast for 5.2 s, or a .fail row inside the view when the failure belongs to it ("experiments.js does not load: …") accent
a long job a Meter with Stop in its row; "Exporting…" in the button's label; a blinking square in a busy pill ink
a selection a 2px accent inset bar on the row; the node's accent outline in the graph accent
nothing to show an ink-2 sentence saying what to do ink-2

Rules

  • Red is earned. Accent marks an error, a bail or the current selection. If two different things are red at once, one of them should not be.
  • Errors carry their place. A diagnostic shows file:line and opens it on click; the runtime banner names the system and the time ("pop/pop stopped at 2.53 s: …") and opens the source.
  • Recover in place. After an exception the world stops at that step; fixing the code and pressing Run resumes from the same moment. Say so in the message ("Fix it and press Run (the world resumes), or Reset.").
  • Do not block. No modal dialogs and no confirmations: destructive actions are undoable (Revert all edits brings the preset back) or say what they remove in their description ("removes your saved preset").
  • Busy without spinners. Progress is a Meter fed by the job, or a 6px square blinking in steps (0.8 s), never a spinner.
  • Disabled, not hidden, when the reason is temporary (Run on other experiments while one runs, Replay before anything is recorded), at 40% opacity; hidden when the control can never apply here (Delete on a built-in preset).
  • Offline features degrade with a sentence. When saving files or Claude is unavailable, say so and offer what still works ("…was copied to the clipboard instead").

ui-copy.md

Writing interface copy

The workbench's words are short, exact and in the program's own vocabulary. They tell a person what a thing is, what a control does, and what just happened, in that order of priority. Every example below is copy from the app.

Names

  • Views are one capitalised word: Notes, Docs, Book, Code, Agent, Reference, Stage, Graph, IR, Traces, Events, Params, Experiments. Each has an about, a lowercase phrase with no full stop: "what this preset is about", "physics and maths, one topic each", "the textbook: Kickflips from First Principles", "the library, editable", "a coding agent with an eval tool", "the API, one page", "the drafting sheet you skate on", "dataflow between systems by phase", "the compiled program as text", "signals and states over time", "tricks, pops, bails, errors", "every parameter, live", "parameter sweeps, headless".
  • Program objects keep their ids and kinds exactly: pop/pop is a system, recognizer/height a signal, pop/snap a param. Write ids in the code face; never translate them into prose names in a control.
  • Parameters show the label written in the code (lowercase, says what it does: "tail snap (nose-up spin the slam starts)", "rider take-off speed") followed by the id's last segment.
  • Presets are code plus title: "B-01 Flatground", "D-03 Onion skins and chronophotographs".

Controls

  • Buttons and menu titles are sentence case, a verb or the thing they make: "Run", "Square up", "Clear", "Reset all", "Save", "Stop", "Export project", "Revert all edits", "Record 20 s of autopilot", "Replay the recording", "Score depth-order strategies…".
  • A label that opens a menu ends with ▾ ("Files ▾", "Export ▾", "Show 4 ▾"); one that opens a file picker or a second step ends with … ("Import project…", "Load clip…").
  • Toggles name the mode: "Track", "Follow", "Freeze", "Edit", "Changed (3)".
  • Every icon button and most buttons have a title that says what happens in a full phrase, with its shortcut: "Recompile the library; the world keeps its state (Ctrl+Enter)", "Step 1/120 s (Shift: 12 steps)", "Reset the world (keeps the code)", "Turn the sheet with the rider's heading", "Stop scrolling (the simulation keeps running)".
  • Menu items carry a lowercase description of the result: "files, notes and settings as .json", "back to B-01 as published", ".epub for Apple Books, Kobo, Calibre and other readers", "a fresh world from this preset's code, run headlessly: the same clip every time".
  • Placeholders say what to type, lowercase: "search the shelf", "search the book", "filter lines", "add a trace: filter signals and states", "new file, e.g. skate/grind.js", "save as my preset: title".

Explanations

A view explains itself in one .lbl sentence in its toolbar, and a menu in a closing note:

  • "Live: a change takes effect on the next step. Edit the code to change a default."
  • "Dataflow: systems by phase, edges carry the states and signals one writes and another reads. Dashed edges: the reader runs before the writer in the step, so it sees last step's value."
  • "Experiments are exported from experiments.js: many headless runs, each a fresh world."
  • "Drag a tab to move it; drop it on a tile's edge to split. The layout is kept in this browser."
  • "Links that drive the workbench become plain text outside it."

Say the mechanism, not a reassurance. "the world keeps its state" tells a person what Run will not destroy.

Numbers

  • A unit after every quantity, separated by a space: "4.29 m/s", "0.08 m", "160 N", "15 rad/s", "0.49 s", "20 s". Angles in the code's own unit.
  • Clocks two decimals ("5.66"), event times three ("2.525"), inspector values three, parameter values as many as they need up to four.
  • Thousands separators on scores ("1,059"). A missing value is "—".
  • Several related numbers in one line are joined by " · " ("flip · shove · wrap" with "-0.01 · 0.01 · 0.00"; "16 systems · 15 signals · 42 states"). A multiplier uses × ("combo ×2", "1×", "0.25×").
  • Status in numbers: "compiled in 7.6 ms · hot: kept 37 states, 4 bodies, 12 system locals, 7 expression states".

Messages

  • Confirmations in the past tense, a few words: "Copied", "Saved as U-01", "Back to the preset as published", "Imported B-01-flatground.json".
  • Errors name the thing, then what went wrong, then what to do: "pop/pop stopped at 2.53 s: … Fix it and press Run (the world resumes), or Reset."; "Saving files is not available here: kickflips-from-first-principles.md was copied to the clipboard instead"; "Nothing recorded yet: turn Record on and let the stage run".
  • Lookups that fail say exactly what was asked for, lowercase: "no chapter 99", "no trace recognizer/hight", "no file skate/grid.js", "unknown lab link …".
  • Empty states say what will be here and how to get it: "No traces pinned. Type above to add one, or click pin trace in the inspector. Every signal and every numeric state is recorded for the last 20 s, pinned or not."; "This preset has no experiments. Add experiments.js exporting Experiment.from(…) values."; "Nothing on the shelf matches."; "No chapter mentions that."; "An empty tile. Open a view:".
  • Unavailable features say so and keep the rest working: "Claude is not available here, so the agent is off. Everything else in the workbench works."

Never

Exclamation marks, emoji, "please", "oops", "simply", "just", jokes, marketing words, title case in sentences, or a message that blames the person.

writing-a-book-section.md

Writing a book section

Kickflips from First Principles is the workbench's textbook: 69 chapters in a front matter, nine parts (I The board and the bench, II Mathematics of moving things, III Physics, IV Tricks, V The program and its runtime, VI Algorithms of the game, VII Drawing, VIII The API and the tools, IX Gameplay and design) and six appendices (A to F). Each chapter is one Markdown file in content/book/, rendered by the Book tab with the same renderer as the notes and exported from there as one HTML page, an EPUB and Markdown. This guide is how to write one chapter, or one numbered section of one, so that it fits the book and passes its checker. The book's own brief is content/book/BOOK-STYLE.md; this page condenses it with the checker's rules and a worked example.

Before you write

  1. Read the chapter's entry in content/book/book.json: its fixed title, its about (the brief: cover all of it), its presets and docs. Read its neighbours' entries so you know what is taught before and after.
  2. Read content/book/FACTS.md: the program's parameters, systems, states, bodies, the trick table and the running example, all generated by node build/facts.js.
  3. Read the chapter's presets (content/presets/<id>.md and the folder beside it) and shelf docs (content/docs/), then the code they point at in src/lib, src/core.js and app/.

The reader and the voice

The reader reads JavaScript and has high-school mathematics: trigonometry, vectors as arrows, the idea of a derivative. Everything else (dot and cross products, quaternions, inertia tensors, impulses, damping ratios, winding numbers, expression graphs, orthographic projection) is introduced in the chapter the plan assigns it to, before it is used. A chapter that needs an earlier idea uses it and links back ([Chapter 9](lab:book?ch=9)) instead of teaching it again.

The model is Peter Norvig's technical writing: foundations first, why before how, concrete before abstract, the reader treated as capable.

  • Start with the point. The first paragraph says what the chapter explains and what the reader will understand by the end. No preamble.
  • Paragraphs develop ideas. Bullets only for lists of parallel, complete sentences.
  • Why, then how. Say what problem a mechanism solves and what breaks without it before showing it. When the design chose, name the alternative and why it lost.
  • Concrete. Real code, real numbers from a run, real event logs; every abstract claim gets an example within a paragraph or two.
  • No analogies or metaphors. Explain a system in its own terms. Skating words are the subject, not a metaphor.
  • Define terms once, in bold where they are defined (winding number), then use them the same way everywhere. Use the program's names: thing, component, site, state, param, signal, system, phase, watch, view, plugin, motor, gesture, intent, stance, guide, recognizer.
  • Rider is the person, board the whole skateboard, deck the wooden part; skater only when naming code (skater/stance). Stance is regular unless you say goofy.
  • Frames: the deck's +x points to the nose, +y out of the grip tape, +z to the toe side. The world's +y is up, gravity −9.81 m/s². One step is 1/120 s, with 8 substeps.
  • British spelling, SI units: "0.49 s", "81 cm" in prose; $9.81,\mathrm{m/s^2}$ with a thin space in maths. En dashes in ranges (1,500–2,500).
  • No em dashes. Use a colon, a comma, parentheses or a new sentence.

Words and phrases the checker flags: delve, it's worth noting, it is worth noting, of course, clearly, obviously, it goes without saying, in this chapter we will, landscape, tapestry, crucial, seamless, robust, leverage, as you can see, it's important to note, imagine, think of it (this, the), like a, just like, magic, nuanced, paramount, embark, journey, simply, basically, essentially, in essence, here's the thing, let's dive, unlock, and the em dash itself.

Figures

A figure is a fenced svg block followed by a caption paragraph that starts **Figure N.k.**. It is drawn in the stage's style: technical drawing, hairlines, ink, grey and one red, on the reader's background.

  • The block starts with <svg and has a viewBox at most 720 wide (viewBox="0 0 640 260" is typical).
  • No literal colours: stroke="currentColor" or the classes ink, mut, acc, hair; fills none or f-ink, f-mut, f-acc, f-fill, f-fill2, f-paper, f-sel. The Figure component lists what each is for.
  • No <style>, <script>, <image>, <foreignObject>; well-formed XML (&lt;, &amp; in text).
  • Text 9 to 13 (font-size="11"); lbl for small uppercase labels, it for variables, b for bold. Maths in labels as Unicode (ω, θ, ½, ², ₀, ·, −, ×).
  • Weights: 1 for outlines, 1.6 for the subject, 0.6 for hatching and construction; dash and dot classes for dashed and dotted.
  • Arrowheads as a marker with an f-ink path; ids are made unique per figure, so arrow is fine in every figure.
  • A figure that claims to show data plots real numbers (from FACTS.md or your own run). A schematic says so in its caption if it could be mistaken for data.

Code

A js block whose first line is a comment naming a file is a quotation, and the checker verifies that every other line appears in that file (whitespace ignored). Name files relative to src/lib (// skate/motors.js, // rigid.js), the runtime as // core.js, the app as // app/draft.js, a preset's own file as // T-05/main.js. Leave lines out with a line that is just // …. Keep quotations to 5 to 30 lines and explain them in prose afterwards.

Code that is not a quotation (a sketch, an exercise's starting point) has no file comment, must run against the real API, and is labelled as yours in the prose. Never invent an API: check names against src/core.js, content/reference.md and the library. Pseudocode goes in text blocks.

Maths

KaTeX, rendered as MathML. Inline $\omega = \dot\theta$ with no space just inside the dollars and no letter right after the closing one; display maths between lines of $$. \begin{aligned}, \tfrac, \mathbf, \hat, \dot, \lVert, \operatorname all work. Inside a table write | as \vert and norms as \lVert … \rVert. A dollar sign that is not maths is \$.

Facts

Every number about the program comes from the program: FACTS.md, or a measurement you describe ("measured headless with test/harness.js, the kickflip gesture in B-01 at default parameters"). Real-world numbers (a deck is about 80 cm long; a street ollie rises 30 to 60 cm) can come from general knowledge, stated loosely. Cite only the classics you are sure of (Newell, Newell and Sancha 1972; Baraff's SIGGRAPH notes; Featherstone; Marey). If the code disagrees with a doc or a note, the code wins: write what the code does and report the difference outside the chapter.

What the checker enforces

node test/book-check.js renders each chapter with the app's renderer.

Errors (the chapter fails): line 1 is not # Title; an unclosed code fence; maths KaTeX cannot parse; an SVG that is not well-formed, does not start with <svg, has no viewBox, uses a literal colour or a forbidden element; a lab: link that does not resolve; a quoted file that does not exist, or a quoted line that is not in it; the renderer throwing.

Warnings: a title different from the plan's; sections not numbered N.1, N.2… in order, or fewer than three; under 1,300 or over 3,200 words of prose; a viewBox wider than 760; a font size outside 8 to 18; a figure without a caption or with the wrong number; fewer than two figures; a preset of the chapter never linked; stray $ in the rendered text; no exercises; any flagged phrase or an em dash.
