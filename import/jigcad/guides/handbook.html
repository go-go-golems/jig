Handbook · method, design system and examples

How to build an executable textbook

An executable textbook explains a body of technique from first principles, with figures computed from the mathematics and a runnable sketch beside every idea. This handbook is the method behind Uncommon Math, a book on the mathematics of the 195 demos at webdev.teknium.io. Part I is the method, in the order you run it. Part II is the Kiln design system the book and its reader are built from, layer by layer, with live specimens. Part III is worked examples: a complete chapter, a sketch gallery, a figure lab, a markdown playground with the chapter checker, a prose clinic and the briefs we used.

Method

The sixteen steps from a pile of demos to a published, runnable book, in the order you run them. Every number and file in this part comes from the Uncommon Math run.

1

What you are building

Four kinds of artifact, one data file, one reader.

An executable textbook has four kinds of content, and keeping them separate is what makes the rest of the method work.

  • A chapter is one markdown file in a small dialect: prose, math, code, tables and callouts. It is written for a reader who is capable but new to the topic, and it explains why before how.
  • A figure is an SVG drawing that lives inside its chapter's markdown, produced by a script that evaluates the real mathematics. Figures use a fixed vocabulary of classes, so one drawing renders correctly in light and dark themes.
  • A sketch is a self-contained JavaScript module that draws one technique on a canvas, with named parameters. The same file runs headless in node, which is how writers check it, and live in the reader, where readers change its parameters and edit its source.
  • A demo is an external thing the book explains, here one of the 195 cards on webdev.teknium.io. The book links to demos, never copies them, and every demo is assigned to exactly one chapter that owns its explanation.

A build step joins these into one JSON file, and a single-page reader renders that file: contents on the left, the chapter in the middle, the bench with sketches and demo cards on the right.

The three kinds of link in a chapter mirror the three kinds of thing a reader can open. lab:demo?id=… opens a demo card on the bench, lab:sketch?id=… loads a sketch into the bench, and lab:book?ch=… jumps to another chapter. They are written as ordinary markdown links, so the source stays readable as plain text.

The pipeline, and what it cost

Twelve stages; the middle one runs once per chapter, in parallel.

The stages split into three phases. Preparation (inventory, dossiers, plan, style guide, briefs) is done once by a coordinator and took about an hour of wall-clock time for 195 demos. Writing is one writer per chapter, running in parallel; each writer researches, computes figures, writes sketches and checks its own work. Assembly (build, reader, archives, the cross-chapter API appendix) is done once at the end.

3

Inventory the subject

One machine-readable record per thing the book must explain.

Start with a list you can count. A book that explains a collection needs to know exactly what is in the collection, so the first artifact is an inventory: one record per demo, with every field the site shows. The site's index page already carries everything, in a regular card structure, so a parser over the saved HTML is enough. Reading the rendered page by eye would have missed most of it: the site's header said 104 demos, but the page contained 195 cards in 20 sections.

Three habits make the inventory trustworthy. Count from the source rather than from a summary: here the section headings each stated their own count (7, 10, 7, 17, …) and the parser's count had to match them. Keep every field, even the ones that look decorative, because writers later quote install lines and licences. Give every record a stable id, because every link in the book is written against it.

Careful. A fetch tool that summarises pages for you will truncate long pages and paraphrase what it keeps. Save the raw HTML with a plain HTTP client and parse it yourself; then the inventory is a fact you can check, not a reading.

4

Mirror the sources and build dossiers

Give every writer the code the demo actually runs.

A book about how things work must be written from what the code computes, and the card blurbs only say what the authors meant. So the second artifact is a mirror of every demo page with all the scripts it loads, followed by a dossier per demo: its inventory record, its own entry bundle, and every GLSL string found anywhere in its dependency graph.

The mirror is a breadth-first fetch: download each demo's index.html, collect the script and stylesheet paths it references, download those, then scan the downloaded scripts for relative import and new URL(…) paths and fetch whatever is missing, until a pass finds nothing new. For 195 demos that was 542 files and 49 MB, and two passes were enough.

Shaders are the richest single source, and they are easy to find: bundlers keep GLSL as template strings, and real shader source always contains void main(, gl_FragColor, fragColor =, a #version line or a precision qualifier. The dossier builder walks each demo's import graph and keeps every template string longer than 80 characters that matches one of those.

5

Group by mathematics, not by appearance

Each demo gets exactly one chapter that owns its explanation.

The site groups its demos by look: dither, retro OS, hand-drawn, React registries. A study book has to group them by the mathematics they share, because that is what a reader learns once and reuses. The Win98 bevels, augmented-ui's chamfered corners and Peel.js's page curl look unrelated, and all three are geometry computed by CSS. React Bits' dithered wave and the Paper dithering shader sit in different site sections and use the same Bayer threshold.

So the plan is a list of chapters by technique, each with a scope paragraph (what to cover), a list of primary demos (the chapter owns their explanation) and secondary demos (mention where relevant). The plan is code, and it ends with an assertion that every demo in the inventory is primary in exactly one chapter.

The resulting 25 chapters fall into eight parts: foundations (spaces, randomness, timing), fields and shapes, image and colour, light, dynamics, marks and type, sound, and machines and the page. Primary counts per chapter ranged from 1 (randomness, differential geometry, spheres) to 16 (CSS geometry). An uneven split is fine. Two smaller decisions matter. Order the chapters so that each depends only on earlier ones where possible, and write that order into the scope paragraphs as cross-references ("why curl noise is divergence-free, forward reference to Chapter 6"). And give every chapter three or four sketch ideas, concrete enough to start from, because a writer who must invent its examples from nothing spends its budget deciding instead of building.

Write the style guide once

Every writer reads the same rules; the rules are checkable where possible.

A book written by twenty-five writers in parallel reads as one book only if they share one specification. The style guide is that specification, and it has seven parts. Each part answers a question a writer would otherwise answer differently.

Write the guide in the voice it asks for, and include exemplars from a book the reader already trusts: here, a figure and a passage from the user's own workbench book, Kickflips from First Principles. Exemplars settle questions of tone faster than rules. Make every rule that can be checked mechanical, and say which tool checks it. "Every figure is followed by a caption starting Figure N.k." is a rule a checker enforces; "explain why before how" is one only a reader can judge, so it gets an example instead.

Brief each writer

Generated from the plan, so every brief has the same shape.

A brief is the writer's whole world: it knows only what the brief and the files it points to contain. Generate briefs from the plan rather than writing them by hand, so that every writer gets the same structure and nothing is forgotten in the twenty-third copy. 8

The voice

Foundation first, why before how, concrete numbers, no analogies.

The book is written in the style of Peter Norvig's technical writing, as the user's own textbook skill defines it, and the same rules go to every writer. Five of them carry most of the weight.

Foundation first. Before a technique, list the terms it depends on and define them in dependency order. Then follow one small example through input, intermediate values and output. A chapter on springs defines the natural frequency and the damping ratio before it compares the three parameter sets libraries use, and then traces one spring, stiffness 320, damping 14, mass 0.8, through all three.

Why before how. Every technique answers a question: what problem does it solve, what would break without it, what do people get wrong about it? The answer goes before the code. A reader who knows why can extend a pattern; one who only knows how can copy it.

Concrete over abstract. Real values, real parameter names, real output. "A 4 × 4 Bayer matrix lights exactly kk of 16 cells for a grey of k/16k/16" teaches; "Bayer matrices distribute pixels evenly" does not. Every number in the text comes from a script the writer ran.

No analogies. Explain systems in their own terms: definitions, equations, code, traces, diagrams. Analogies hide the details that matter and break exactly where precision is needed.

No filler. No preamble, no hedges, no "it is worth noting", no "of course". Every bullet is a complete sentence that could stand alone. The reader is capable.

Before · opening a chapter

In the ever-evolving world of web graphics, dithering has become an increasingly popular technique. In this chapter, we will explore the fascinating history and mathematics of dithering, delving into ordered dithering, error diffusion, and much more.

After

A display that can show only a few levels of grey turns a smooth gradient into bands. Dithering trades those bands for texture by adding a pattern before the threshold. This chapter derives the two families every demo here uses, ordered thresholds and error diffusion, and measures what each one costs.

The rewrite starts with the problem, names the mechanism in one sentence, and says what the reader will be able to do. More pairs are in the prose clinic.

The shape of a chapter

Lead, foundations, techniques, a reusable API, then three closing sections.

Every chapter has the same skeleton, so a reader who has finished one knows where to look in the next, and the build can find the parts it needs.

  1. Title and lead. One # Title line, then one paragraph that states the problem, names the mechanism and says what the reader will be able to do afterwards. The renderer prints the lead in grey and puts the section list under it.
  2. Foundation sections. The definitions and derivations the techniques need, in dependency order, each grounded in one worked example with real numbers.
  3. Technique sections. For each technique: the concept and why it exists, the mathematics, the algorithm as js or text pseudocode, a worked trace, a figure, where it appears in the demos with the parameter that maps to each symbol, a Try it linking a sketch, and an Exercise where one helps.
  4. Toward a reusable API. The small vocabulary of types and functions this domain reduces to, as signatures with one-line semantics. These sections are later merged across chapters into the book's domain APIs (step 14).
  5. Demos in this chapter, a table of every primary demo and the secondary ones discussed, with the section that covers each.
  6. Key points, six to ten complete sentences that summarise and add nothing new.
  7. Further reading, five to twelve sources the writer actually opened, each with one line on why to read it.

Figures are computed

A script evaluates the real mathematics and prints the SVG.

A figure drawn by eye shows what the author believes; a figure computed from the formula shows what is true, and the two differ more often than you would expect. So the rule is absolute: every curve, point and label position comes from a script that evaluates the mathematics or runs a port of the library's code, and the writer rounds coordinates to 0.1 and pastes the output into the chapter.

The script below produced Figure S.1 in the worked chapter. It is typical in three ways. The panels share a mapping from data to pixels (X, Y), so ticks and curves cannot disagree. function panel(x0, y0, w, h, ymin, ymax, key, title, ticks) {

The checking loop for figures is mechanical up to the last step. The chapter checker parses each SVG, rejects anything the reader's sanitiser would strip (scripts, style elements, external hrefs, image), rejects classes outside the figure vocabulary, warns on hard-coded colours, and requires the caption. Then it injects a stylesheet that maps the classes to the light theme, renders every figure to a PNG with resvg, and writes them to a folder. The last step is not mechanical: the writer looks at every PNG and fixes overlapping labels, clipped text and wrong constructions. Several writers reported fixing label overlaps this way; a checker that only parses would have passed them.

Figures in the book are drawings for reading, not decoration: a construction (Snell's law at a boundary), a comparison (three blur kernels side by side), a sequence of states (FLIP's First, Last, Invert, Play), or a parameter sweep (overshoot against damping). Run the writers

Waves, progress you can see, and messages that change course.

Concurrency. The session allowed 20 writers at once, so the run went in two waves: twenty started together, and each of the last five started the moment a first-wave writer finished. If you have more chapters than slots, put the chapters you most want checked in the first wave; late starters are the ones that receive any mid-run change of plan earliest in their work.

Progress. Writers report only when they finish, two to three hours later, so watch their files instead. Every writer has a scratch folder and an output folder; the modification time of the newest file in each tells you who is working and who has stalled, without reading any transcript. Two hours into the run, 17 of the 20 first-wave chapters already had sketches on disk, which meant their research was largely done and drafting had started.

Changing course. A message to a running writer is queued and delivered at its next tool call, together with any other queued messages. Two consequences follow. The writer acts on the combination of everything you sent, so decide the policy before you broadcast it: in this run three messages went out within two minutes (finish fast with short limits; correction, no limits but no new research; keep everything you have), and at least two writers had already produced condensed versions they then threw away. And a message is a request, not a stop: a writer partway through a figure finishes the figure first.

Budget. The cheapest lever is research. At 19:15 the instruction "no more web searches or fetches, no downloads, no further reading of sources beyond what you already have" cut the remaining work sharply: the five second-wave writers ran 49 to 67 minutes against two to three hours for the first wave. Independent review was planned (one reviewer per three chapters, re-checking math against scripts and library claims against dossiers) and was called off; the reviewer that had started was stopped before it changed anything.

Restarts. The workspace restarted once, while the appendix writer was working. Everything on disk survived, and the writer resumed from its saved transcript; only work not yet written to disk had to be redone. Tell writers to write their chapter file early and update it, rather than assembling it in memory at the end.

Careful. A writer's final report is not shown to the person who asked for the book. Relay what matters as each chapter lands: what it covers, what it found in the libraries' code, how many figures and sketches it has, and what it could not verify. In this run those per-chapter notes were where the most interesting findings surfaced first.

Kiln design system

The visual system of the reader and of every figure in the book, from tokens to the full reader shell. Each specimen below is live markup using the same stylesheet as the reader; flip any specimen between light and dark with its own switch, and copy its source.

Principles

Seven decisions every component follows.

Kiln is the look of the user's Form Skate Workbench: Swiss in spirit, built for reading technical material for a long time without fatigue. Seven decisions define it, and every component below follows from them.

  1. One ground, one ink, one accent. The page is white (or near-black in dark mode), text is ink, and there is a single red. Panels are separated by 1 px rules, not by tinted backgrounds; the one tint, --fill, marks code, callouts and hover rows.
  2. Red has four jobs and no others. It marks errors, the current selection or item, links into the bench (the ▸ after a lab: link), and in a figure the one curve or point the caption is about. A red that decorates dilutes the four that inform.
  3. Arial in two weights, monospace for code. Hierarchy comes from size, weight and rules, never from typeface changes or colour. Uppercase labels at 10.5 px with 0.06 em tracking name things without competing with headings.
  4. Square, flat, ruled. No border radius, no shadows, no gradients in the interface. A heading is introduced by a 1 px ink rule above it; a frame is a 1 px hairline.
  5. Dense where you operate, measured where you read. Interface text is 12 px; reading text is 13.5 px at 1.65 line height on a 76-character measure.
  6. Everything is a token. Components and figures name roles (--ink, mut, acc) rather than colours, so a theme change is a change of token values and nothing else.
  7. Numbers line up. Anything that counts, measures or times uses tabular figures.

S.2 Smoothstep from four conditions

To remove the jump in slope, ask for a polynomial f(s)f(s) on [0,1][0, 1] whose value runs from 0 to 1 and whose slope is zero at both ends. That is four conditions:

f(0)=0,f(1)=1,f′(0)=0,f′(1)=0. f(0) = 0, \qquad f(1) = 1, \qquad f'(0) = 0, \qquad f'(1) = 0 .

smoothstep⁡(s)=3s2−2s3=s2(3−2s). \operatorname{smoothstep}(s) = 3s^2 - 2s^3 = s^2 (3 - 2s) .

Prose clinic

Eight rewrites in the house voice, each with what changed.

Before · a hedged claim

It could be argued that error diffusion may potentially produce somewhat better results than ordered dithering in certain scenarios, although this might depend on various factors.

After

Error diffusion reproduces tone more accurately than ordered dithering, because it carries each pixel's rounding error to its neighbours instead of discarding it. Ordered dithering is still the right choice on a GPU, where every pixel must be computed independently.

State the claim, give the reason, and name the case where the other choice wins. Hedges add words and remove information.

Before · an analogy

Think of a spring animation like a rubber band: when you pull it and let go, it snaps back and wobbles a bit before settling down.

After

A spring animation integrates mx¨+cx˙+k(x−xtarget)=0m\ddot x + c\dot x + k(x - x_\text{target}) = 0 every frame. With damping ratio ζ=c/(2km)\zeta = c/(2\sqrt{km}) below 1 it overshoots by exp⁡(−πζ/1−ζ2)\exp(-\pi\zeta/\sqrt{1-\zeta^2}), 21.7 % for Motion's stiffness 320, damping 14 and mass 0.8, and then settles.

The analogy explains nothing a reader can compute with, and it breaks exactly where it matters: a rubber band has no damping ratio. The rewrite gives the equation, the one number that decides the behaviour, and a worked value from a real library's defaults.

Before · vague bullets
  • Important performance considerations
  • Key differences between approaches
  • Things to watch out for
After
  • A separable Gaussian blur costs 2n2n texture reads per pixel instead of n2n^2, so a 9-tap blur drops from 81 reads to 18.
  • Kawase blurs reach a similar width with 4 reads per pass by sampling between texels, at the cost of a less exact profile.
  • Blurring in sRGB instead of linear light darkens edges between bright and dark regions.

Each bullet in the first list names a topic; each bullet in the second states a fact the reader can act on. A bullet must be a complete sentence that could stand alone.

Before · an abstract claim

Bayer matrices distribute the threshold values evenly, which produces a pleasing, regular pattern for every grey level.

After

A 4 × 4 Bayer matrix holds each threshold 0,1,…,150, 1, \dots, 15 once. A flat grey of k/16k/16 therefore lights exactly kk of the 16 cells in every tile, so the average over a tile reproduces the grey exactly, and the matrix is ordered so that the lit cells for each kk are as spread out as possible.

"Evenly" and "pleasing" are judgements; the rewrite gives the property that makes them true, with numbers the reader can verify by counting.

Before · how without why

To animate a layout change with FLIP, record the element's first position, apply the change, record the last position, apply an inverse transform, and then animate the transform to zero.

After

Animating top, left, width and height forces the browser to recompute layout on every frame, which costs milliseconds per frame on a busy page. FLIP avoids that by letting layout happen once: it records the element's First box, applies the change, measures the Last box, Inverts the difference with a transform so the element appears not to have moved, and then Plays the transform back to zero, which the compositor animates without layout.

The steps are the same in both. The rewrite first says what problem the technique solves, so the reader knows when to reach for it and why each step exists.

Before · a claim about a library

Paper's dithering shader uses standard ordered dithering with a Bayer matrix.

After

Paper's dithering shader computes dithering = M / n² - 0.5 and lights a cell when shape + dithering reaches 0.5, that is when shape≥1−M/N2\text{shape} \ge 1 - M/N^2. The centred rule uses (M+0.5)/N2(M + 0.5)/N^2; dropping the half step biases average coverage by −1/(2N2)-1/(2N^2), which is −0.031-0.031 on a 4 × 4 matrix. At a grey of 0.3, Paper lights 4 of 16 cells where the centred rule lights 5.

The first sentence could be written without reading the code; the second could not. Claims about a library come from its source, and the most useful ones are where it differs from the textbook. The rewrite is condensed from Section 11.2 of the book.

Before · a caption that restates

Figure 4.4. A plot of fBm noise and its spectrum.

After

Figure 4.4. Left: four octaves of 1-D gradient noise with gain ½ and lacunarity 2, and their sum (red). Right: the power spectrum of six-octave sums, averaged over half-octave bands and three seeds. Above the lowest octave's band both are straight lines on log-log axes, with slopes close to −(2H+1)-(2H+1).

A caption is where the teaching happens: what is drawn, how it was obtained, and what to look at. "A plot of" tells the reader nothing the figure does not. The rewrite is the book's real caption.
